# 平台薄弱点与多云推进清单

更新日期：2026-11-15
范围：本地开发和隔离测试；不代表生产节点、真实支付或线上调度已上线。

## 当前基线

- AWS 是唯一已经接入自动创建、验收和资源回收驱动的云厂商。其他厂商尚未连接 API，也没有可用的生产凭证。
- AWS 隔离测试已经验证过真实节点出网和资源释放；WireGuard 测试只证明该隔离节点的协议路径可用，不等同于会员凭证发放、会员计量或客户端断线验收。
- 控制面已按 `NodeProvider` 抽象服务商生命周期。本轮已在本地实现 AWS 部署档案目录和账号/区域/版本固定校验；目前目录里只有 AWS 测试档案，未接入其他服务商。
- pd01、pd02 是受保护的控制面/业务主机，不进入 VPN 节点整机回收流程。
- 本地沙箱退款可撤销本地权益和订阅；本地已增加会员设备登记与名额限制，但真实会员节点 peer 撤权驱动及线上常驻 worker 尚未接入。

## 薄弱点清单

## iGuge 可借鉴的产品流程

以下是已了解到的用户侧行为，不代表对 iGuge 后台实现的核实：

1. 购买完成后账户直接关联一条长期固定的订阅凭证；续费延长权益，客户端不必重新生成订阅地址。
2. 浏览器扩展识别当前登录账号，VIP 入口进入付款流程；付款后刷新会员到期时间。
3. 订阅凭证可复制或扫码导入兼容客户端；不同客户端有各自的导入入口和说明。
4. 网站、扩展和客户端围绕同一个账户/订阅状态工作，不让用户理解服务商节点、云账号或部署细节。

本站应借鉴这些用户体验原则，后台仍使用自己的支付、权益、节点和客户端实现，并保留真实状态、失败原因与恢复流程。

## 推进顺序与放行门

### 1. 固定多云部署目标

服务商档案需包含服务商、不可变档案 ID/版本、账号 ID、区域、允许规格、协议能力、网络配置引用和凭证引用。数据库部署任务保存目标快照；任何创建、探测、配置下载、下架或重试都必须从该任务解析原档案。默认服务商变更不得改变旧任务目标。档案版本变化时创建新档案 ID，旧档案保留到关联资源全部释放。

### 2. AWS 驱动收口

完成 AWS 档案目录、账号/区域一致性检查、CloudFormation 资源清单、创建/释放幂等和失败清理。用隔离账号/实例跑通新建、协议验收、回收和残留盘点；不使用根用户作为线上常驻身份，不把本机 AWS profile 搬到服务器。

### 3. 第二家厂商实验

先比较目标用户真实网络质量、区域、供应商 AUP、数据中心出口、带宽计费、API 配额、支持能力和删除语义，再确定厂商。用短时专用实例跑相同 conformance suite，核对服务器、磁盘、网卡、公网 IP、安全组、防火墙、密钥和计费项全部释放。无真实实验结果时，后台只能显示“未接入”，不能显示“自动部署可用”。

### 4. 新旧节点替换

先预检容量和费用，再创建新节点；通过控制面、协议和客户端真实验收后发布新订阅配置；观察拉取和连接指标；异常时恢复旧配置；稳定后停止旧节点接收新连接，等待缓存/会话排空，最终撤销 peer 并核对账单、释放资源。任何一步失败均保持旧节点可恢复，不能自动越过验收门。

### 5. 会员准入

多云自动化和蓝绿替换通过隔离测试后，再接入会员设备凭证、权益鉴权、流量计量、退款、限设备和客服处理。确认每个平台实际断连语义后才允许向用户开放对应节点。

## 本轮验收记录

- 服务商档案及后台选择器：本地实现；档案路由和身份校验已覆盖。
- 服务商契约：AWS PHP 适配器通过本地假执行器契约测试；真实 AWS API 没有在本轮调用，契约未证明多云 API 行为。
- 节点发布门槛：探测即使返回 `verified=true`，也必须提供合法 IP 地址才会发布为可用；无效结果维持候选并走现有重试。
- 第二家服务商：未接入。
- 线路版本发布：本地已实现草稿、灰度、发布、旧版本排空标记、回滚，以及线上 scheduler 可调用的排空版本自动收口；尚未与云节点自动部署任务做一键蓝绿编排。
- 节点蓝绿替换：未完成；当前仍需人工先验收节点，再在后台线路发布面板操作。
- 会员设备登记与名额控制：本地已完成；真实客户端身份绑定、节点 peer 自动开通/撤销、流量计量和真实退款撤权：未完成。
- 生产常驻 worker 与告警：未部署。
