# 迅连宝 VPN 业务、研发与运维路线图

本文用于把当前本地演示平台拆成可评估、可实施、可验收的工作。当前代码仍是本地 MVP：测试节点、订阅、订单和佣金数据均为演示数据；没有真实隧道、支付、退款、结算、客户端或线上运维能力。

## 0. 上线前置门槛

面向中国大陆用户提供 VPN、跨境网络接入或相关服务，必须先让熟悉目标业务和地区的律师及合规负责人书面确认经营主体、服务范围、必要资质、网络与数据处理要求、支付和应用商店政策。本文不构成法律意见。在门槛未通过前，只做本地开发、测试和经授权的封闭试点；不得把演示节点或测试订阅用于真实连接或对外售卖。若拟议服务不符合适用要求，应调整为经批准的企业远程接入或其他合规产品，或停止该服务范围。

上线审查还应明确：服务地区和允许用途、服务商与云厂商合同、隐私政策和用户协议、日志最小化与保留周期、数据访问审批、退款和投诉机制、未成年人及滥用处理规则、跨境数据路径、应用分发渠道政策。任何营销承诺都要和实测的覆盖区域、速度、可用率、设备数、退款政策一致。

## 1. 业务闭环

用户路径应从一个可解释、可支持的承诺开始：了解产品和限制 → 注册并验证账户 → 选择套餐 → 支付确认 → 权益生效 → 安装自有客户端或导入受支持的第三方客户端 → 连接与查看状态 → 续费、退款或取消 → 获得售后支持。

服务端是订单、权益、设备、订阅凭证和用量的唯一事实来源。支付回调要验签、幂等并可补偿；不能因浏览器跳转就发放权益。退款、拒付、过期、封禁、续费失败和代理佣金冲正都要有明确状态机、审计记录及人工复核路径。佣金使用不可变流水记账，退款时新增冲正记录，不改写历史金额。

用户侧应提供订单与付款状态、套餐权益及到期日、设备管理、订阅创建/轮换/撤销、客户端安装与导入指引、服务状态公告、工单入口和账户安全操作。管理端至少需要角色权限、MFA、操作审计、用户与权益、订单/退款只读及受控操作、节点目录、订阅策略、工单、公告、代理账本和报表。高风险财务、凭证和节点操作应双人复核。

## 2. 用户常见问题与支持流程

| 用户问题 | 首轮排查 | 处理原则 |
| --- | --- | --- |
| 付款成功但没有权益 | 用订单号核验支付渠道回调、幂等键和权益流水 | 可重放安全的发放任务；不索要完整银行卡或支付口令 |
| 付款处理中或重复扣款 | 核对渠道状态、商户订单号和退款状态 | 以渠道账单为准；重复回调不得重复发权益 |
| 订阅无法导入 | 确认客户端名称/版本、订阅是否有效、网络能否访问订阅域名 | 提供对应版本步骤；不要让用户公开粘贴完整订阅 URL |
| 导入成功但不能连接 | 核对账户权益、订阅更新时间、协议支持、节点公告和客户端日志中的脱敏错误 | 区分账户、配置、客户端和节点故障；收集时间、系统、版本与错误码 |
| 能连但速度慢/延迟高 | 对比地区、时段、网络类型、单设备与多设备、节点负载和探测结果 | 先判断本地网络还是节点拥塞；公告影响范围和恢复进展，不承诺未经验证的速度 |
| 某地区或网络无法使用 | 检查服务公告、运营商/网络环境、DNS、时间同步和客户端配置 | 说明支持范围和已知限制；不建议关闭系统安全防护或安装来历不明配置 |
| 订阅更新后仍指向旧节点 | 确认客户端自动更新周期、手动更新结果和配置版本 | 通过稳定订阅 URL 发布版本；旧节点 drain 期内保留容量并提供回滚 |
| 设备数已满 | 展示已登记设备、最近活跃时间和移除入口 | 用户可撤销旧设备；异常重置需身份验证并留审计 |
| 到期、续费或退款争议 | 展示套餐周期、权益开始/结束时间、续费授权及渠道记录 | 依据清晰的服务条款和当地消费者规则处理，保留可追溯工单 |
| 账户或订阅泄露 | 撤销会话和订阅凭证、检查审计与异常访问 | 订阅 URL 等同秘密；支持人员不得索要或在工单中回显完整 URL |

工单模板只收集排障必要信息：账户 ID（避免收集密码）、订单号、发生时间及时区、客户端/系统版本、网络类型、节点代号、错误码和脱敏日志。不要收集订阅密钥、支付凭证、完整流量内容或无关个人信息。P0（大面积不可用、疑似数据/密钥泄露、支付异常）立即升级值班负责人；P1（区域或核心功能显著受损）进入当班响应；普通单账户问题由客服按标准流程处理。先确认收到，再按影响范围更新状态和预计下次更新时间。

## 3. 节点生命周期与多节点稳定性

生产控制面和节点数据面应分离。控制面存放节点目录、期望配置、容量策略、健康状态和变更记录；数据面只执行获批配置。节点密钥放在专用密钥管理系统，不能写进仓库、普通订阅模板、日志或工单。订阅签名密钥与节点密钥分离并支持轮换。当前 SQLite、单 API 进程和保留测试地址只适用于开发，不适合作为生产控制面。

节点台账至少记录：稳定 node_id、服务商/资源账户、区域、协议和软件版本、网络入口、容量上限、当前状态（候选/测试/可用/排空/维护/隔离/退役）、健康检查时间、配置版本、密钥引用、负责人、变更单和回滚目标。管理页面显示采样时间，避免把过期健康数据标成在线。

新增节点：

1. 建立变更单，说明业务原因、合规范围、资源提供方、区域、容量、成本、风险、负责人和回滚条件。
2. 在隔离测试环境部署，完成基线加固、补丁、端口/防火墙审查、证书和密钥配置、时间同步、监控、日志脱敏、容量和恢复测试。
3. 验证目标客户端与协议矩阵、DNS/路由/MTU 等实际网络行为；测试数据不得连接到真实用户权益。
4. 先加入候选池，再用内部测试账户验证；检查连接成功率、握手时间、延迟、丢包、CPU/内存、带宽、连接数和错误率。
5. Canary 放量并观察至少一个完整业务高峰周期；指标达标且值班人批准后再逐级扩容。

节点替换/下线：

1. 先确认新节点容量和健康度已达标，目标区域有冗余；变更期间不得先撤掉唯一可用容量。
2. 将旧节点标记为排空，停止新连接，保留存量会话和足够的迁移窗口；通过稳定订阅地址发布可回滚的配置版本。
3. 分批引导用户客户端更新或调整服务端调度；监控新旧节点连接成功率、失败率、延迟、客服量和剩余容量。
4. 到达回滚阈值时恢复旧路由/配置版本并停止扩量。确认稳定后才隔离旧节点、撤销密钥、清理资源并核对账单。
5. 关闭变更单，记录前后指标、异常、实际影响、回滚结果和改进项。

健康探测至少组合控制面心跳、TCP/协议握手、外部合成连接、区域延迟/丢包、资源水位和真实错误率。单个 ping 成功不等于服务可用。调度要考虑容量余量、区域隔离、故障域和熔断；告警分级并做去重，自动化只执行经过演练的低风险动作。新节点验证、证书/密钥轮换和配置发布要可暂停、可回滚且留审计。

## 4. 软件、配置与节点发布流程

环境分为本地开发、集成测试、预发布和生产，各环境账号、密钥、数据库、订阅域名、支付沙箱与真实商户完全隔离。生产变更从代码审查通过的不可变版本构建；记录提交号、依赖锁文件、构建产物摘要、配置版本、数据库迁移和审批人。

每次发布的检查点：

1. 变更单包含影响用户、风险、维护窗口、验证步骤、负责人、监控面板和回滚条件。
2. CI 通过类型检查、单元/集成测试、权限与安全检查、依赖扫描、构建和数据库迁移兼容性检查。
3. 预发布环境按真实流程验收注册、支付沙箱、权益发放、订阅轮换/撤销、节点故障切换、退款补偿和客户端导入。
4. 数据库采用向前兼容的 expand/contract：先加兼容字段/表，发布读写逻辑，迁移完成并观察后再移除旧结构。先验证备份可恢复。
5. 先对内部账户或小比例流量 Canary，检查连接成功率、API 错误率、支付/权益对账、订阅获取、节点余量、客服工单和资源水位，再逐级扩量。
6. 超过预设错误阈值、对账不平、数据损坏迹象或节点余量不足时立即停止扩量并回滚。回滚方案需区分应用回滚、配置回滚、路由回滚和数据库前向修复；不可盲目回退已发生的支付或账本事实。
7. 发布后完成用户关键路径抽测、支付渠道与内部账本对账、节点探测、告警确认和工单观察；当班人签字关闭变更并做简短复盘。

紧急热修也要有变更编号、双人复核、最小修改、自动化检查和事后复盘。维护公告注明影响产品、区域、开始时间、已知影响、用户操作、恢复状态和下次更新时间，不暴露基础设施秘密。

## 5. 客户端和第三方兼容策略

建立受支持矩阵，记录操作系统、客户端名称/版本、核心版本、配置格式版本、导入/更新/切换/到期/撤销结果和测试日期。Clash Verge Rev、Clash Mi 只在实际版本和合规服务环境验证后才能标记“支持”；不能根据 YAML 能生成就宣称兼容或可连接。

Android 自有客户端需要评估 `VpnService` 权限、前台服务/断线恢复、按应用路由、DNS 泄漏保护、耗电、系统版本差异和 Play/厂商商店政策。iOS 需要评估 Network Extension entitlement、签名/分发资格、系统连接审批、后台恢复、隐私披露和 App Store 审核规则。桌面应用需明确更新签名、配置迁移、崩溃回报和卸载清理。浏览器扩展通常只能管理账户、订阅或浏览器级代理能力，不能替代 Android/iOS 系统隧道；需单独审查浏览器商店权限和隐私政策。

## 6. 指标、值班和运营节奏

先建立可计算且来源明确的指标：节点可用率、端到端连接成功率、连接建立时间 P50/P95、区域延迟/丢包、节点容量余量、订阅拉取成功率、支付回调延迟、权益发放失败数、对账差异、退款率、每千活跃用户工单数、首次响应时间、续费率和流失率。每个指标注明分母、采样窗口、剔除条件、数据保留期和负责人；不要把探测数直接包装成客户 SLA。

- 每日：值班人看告警、节点容量、失败连接、支付回调/权益队列和未处理 P0/P1 工单。
- 每周：运营与研发复核工单 Top 5、退款/拒付、续费与流失、节点成本与区域表现、发布和事故复盘。
- 每月：访问权限和密钥轮换审查、备份恢复抽测、供应商账单核对、灾备演练、隐私/数据保留审查和容量预测。
- 每季度：客户端/核心版本兼容、渗透测试与依赖风险复核、事故桌面演练、合同和合规范围复查。

最小责任分工：产品/运营负责服务边界、套餐、公告和工单知识库；客服负责身份核验和标准排障；后端负责账户、支付、权益、订阅和账本；SRE/网络负责节点、容量、监控、变更和恢复；安全/合规负责人审核数据与权限；财务负责支付对账、退款及佣金复核。小团队可一人多岗，但生产高风险操作不能由同一人提出、执行并最终批准。

## 8. 开发执行队列（2026-11-08 更新）

本轮已完成并本地验收：控制台深浅主题与字号调整；测试节点生命周期；会员测试订单创建/取消/到期；管理员订单筛选、分页与详情弹框。订单采用服务端计价、购买时套餐快照和用户范围幂等键。测试订单不会调用支付渠道、发放权益或生成佣金。

### 下一批：支付事件与权益闭环

1. 先固定业务规则：续费是延长到期日还是生成独立权益；同套餐续费时流量是否重置；是否允许跨套餐升级；设备数限制如何执行；退款是否按剩余时长/流量折算。未确认前，先做独立的本地事件处理和账本，不自动合并真实权益。
2. 建立支付适配器边界与本地测试驱动：商户订单、渠道交易号、金额/币种、回调验签、时间窗、重复及乱序消息、主动查单、对账和补偿。没有商户资料也能先完成本地契约测试，不能以浏览器“支付成功”跳转或管理员改状态代替渠道确认。
3. 建立权益发放流水：一笔确认付款最多发放一次；订单、支付事实和发放结果分别记录；失败可重试；过期订单收到延迟付款要进入异常处理，不能悄悄丢单。退款/拒付采用补偿流水。
4. 接前后台界面：付款中、失败、待核验、待发放、已生效、退款中及异常工单入口；新建、详情和操作确认均使用弹框。

验收：错误签名、金额不符、重复回调、乱序回调、超时后付款、发放失败重试、退款补偿均有自动化用例；会员看不到他人订单；对账能解释每笔差异。正式渠道接入另需商户的沙箱资料和回调契约，不能把本地模拟结果标成渠道联调成功。

### 并行准备范围：运维与安全基础

- 管理权限拆分为客服、运营、财务、节点运维；管理员 MFA、会话管理、敏感操作二次验证；所有变更留审计。
- 数据库准备：选择正式数据库，验证并发下单/取消/回调竞态、唯一约束、时区、迁移和备份恢复。本地 SQLite 检查不等于生产数据库验收。
- 节点先做只读探测和状态新鲜度，再做配置版本、变更预览、发布审批、灰度和回滚。控制面标记“可用”不能代替实际协议探测。
- 新测试节点优先使用隔离资源；pd01 当前承载已有服务，pd02 的访问权限与连接条件仍待解决。现有服务器上不直接安装或重启节点服务。

验收：过期探测显示未知/陈旧；单节点故障可隔离；配置回滚有审计；恢复演练能恢复数据；操作不影响现有线上服务。
